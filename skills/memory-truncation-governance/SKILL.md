# 记忆注入截断治理

## 机制（实测，不是推测）

注入内容末尾会留一句 `(memory truncated — MEMORY.md is too large)`。
**拿它前面最后那句话回原文搜索定位偏移，就反推出了注入预算**——这是整套治理的测量方法。

实测数据（2026-09-20，同一台机器两个文件）：

| 文件 | 全文 | 实测断点 | 丢弃占比 |
|---|---|---|---|
| 项目 `.workbuddy/memory/MEMORY.md` | 24,310 字符 | 第 8,471 | **65.2%** |
| 用户级 `~/.workbuddy/MEMORY.md` | 13,140 字符 | 第 3,984 | **69.7%** |

**三个反直觉但决定性的结论：**

1. **它是「从头保留、尾部丢弃」**，不是均匀抽样或智能摘要。
   而记忆文件是**追加式**生长的（越靠后越新）→ **丢的恰好是刚写的最新结论**。
   最讽刺的一次：用户级丢掉的正是「★★ 数据交叉验证铁律（最高优先级）」整节。
2. **系统提示里的 `Limit: N chars/session` 指的是注入预算，不是写入限额。**
   证据：用户级声明 4,000，实测断点 3,984，几乎正好用尽。
   ⚠ 项目级声明 3,000 但断点 8,471——两者相加 12,455 看着像共享预算，也可能按 token 计，
   **这条没有证据，别当结论用**；每次要按上面的方法自己实测。
3. **host 侧的注入行为改不了**，唯一可控变量是**文件体积**。

## 治本：去冗余，不是压缩

单纯压缩会把"记得很细"和"记得住"对立起来。正确做法是分层：

```
MEMORY.md  ← 只注入这一份，必须苗条。放：导航 + 不可替代的规则 + 一引用就错的口径
├── MEMORY_全文_YYYY-MM-DD.md   ← 治理前原文，零删改，只归档不注入
├── 关键事实.md / 环境事实.md / 历史轮次.md …  ← 按主题拆出，需要时才读
```

**索引卡里只留三类东西**（其余一律"去哪读"）：

| 留 | 因为 |
|---|---|
| **导航表**（想查 X → 去哪个文件） | 没有它，拆出去的信息等于丢了 |
| **不可替代的项目特有规则** | 每次回答都要遵守，必须常驻 |
| **一引用就错的口径**（如市值三口径、停牌占位行） | 不常驻就会算错，且错得很隐蔽 |

**目标体积**：实测断点的 **≤50%** 最稳（留足后续追加空间）。

## 执行流程

1. **实测断点**——从会话里注入内容的最末一句回原文定位。不要沿用旧数字。
2. **全文备份**：`cp MEMORY.md MEMORY_全文_YYYY-MM-DD.md`。**先备份再动手**，备份本身就是零丢失的兜底。
3. **按标题脚本切分**（不要手抄）：
   ```python
   # 按一级 "## " 切 → [(title, body)]，按「标题包含关键字」路由到目标文件
   # 关键字路由比精确匹配稳：标题常含 ★、（）、日期后缀
   ```
4. **写索引卡**：重写那部分保留内容，允许改标题（更贴合新结构）。
5. **双向验收**（见下）。
6. **接守卫**（见下）。

## 双向验收（缺一不可）

**① 信息零丢失**——原文每个小节都必须可寻址，三种命中方式：

| 命中方式 | 说明 |
|---|---|
| 原样保留 | 标题逐字相同 |
| 标题改写后仍在 | 取标题前 4 字做包含匹配 |
| **显式登记出处** | 标题差异太大或被降格为正文条目时，**人工登记"→ 现在在哪"** |

> ⚠ **登记时必须同时给出锚点字符串，并在正文里真找到它**。
> 治理那次我登记了一条，锚点比实际文本少了两个星号（`数据交叉验证铁律（` vs `数据交叉验证铁律**（`），
> 机器当场报"已登记但锚点未找到"。**这就是这道闸的价值——它校验的是登记是否真的对得上，不是有没有登记。**

**② 引用路径有效**——提取索引卡里所有 `` `...` `` 路径逐个 `os.path.exists`。
**指错路 = 另一种形式的信息丢失**，而且更隐蔽（看着有出处，点进去是空的）。

过滤误判的规则（实测必需的几条）：跳过含换行的片段（嵌套反引号会跨段匹配）、
跳过含 `YYYY`/`XXX` 的占位符、只认带扩展名或以 `/` 结尾的路径形态。

## 常驻守卫

写只读守卫脚本（超注入断点即 exit 1，**绝不自动改写文件**），接进项目的重跑链：

```python
TARGETS = [("项目 MEMORY.md", PROJ_MEM, 8471), ("用户 MEMORY.md", USER_MEM, 3984)]
WARN_RATIO = 0.70   # 预警线，超过提示；超过 cut 才判失败
```

本项目已接为 `体系/run_all.py` 第 7 步，`--skip-fetch` 实测 6 步 / 2 秒。

## 进阶：把整个 memory 目录冷凝

索引卡瘦下来只是第一步。实测治理完的项目 memory 目录仍有 **277 KB**——
因为里面堆着历代 bak、windbak、治理前全文。它们不被注入，但会让目录无法阅读，且**埋着你迟早会误引用的旧数字**。

### 判冗余：行级覆盖检查（不要用"看着像"来判断）

把候选文件每一行（去标题装饰、长度 >12）拿去参照集合里**当子串找**，找不到才算"独有"：

| 候选 | 覆盖 | 未覆盖的行是什么 |
|---|---|---|
| `2026-09-19.md.windbak` | 100% | 纯副本 → 直接归档 |
| 治理前 `MEMORY_全文` | 87% | 被重写进索引卡的几节（信息在，**措辞变了**） |
| `MEMORY.md.bak*` | 77%~89% | **已被推翻的旧口径 / 已完结的待办** |

⚠ **不要用 md5 找重复**——历史版本都是修改过的，md5 全部不同，漏判干净。
**要按"行是否已在别处"判**，这才对应"信息是否丢失"这件事。

### 提炼：真正该从旧记忆里抢救的是「已废止口径」

旧文件唯一不该丢的东西，不是旧结论，而是**"哪些数字曾经是这么说、后来被推翻了"**。
它们的危险在于**引用即错，而且错得很像真的**。

建一张 `口径变迁台账.md`，两节结构：

- **§一 已废止口径（引用即错）**——三列：`废止值 | 现行值 | 差异`。
  实测最凶的一例：A/H 溢价用固定汇率算的中位是 **+172.96%**，逐日中间价口径是 **+118.03%**，
  **虚高 54.9pp**——而这个旧数一直躺在 bak 里。
- **§二 仍然有效的方法论结晶**——从旧文件里挑出至今成立的（如"体系"的判定标准、逐年匹配基准的原则）。

### 归档而非删除，日志留够 30 天

- 已验证冗余的文件 → `归档/YYYY-MM-DD_记忆冷凝/`（**移走，可逆**）。是否永久删除交用户拍板。
- **`YYYY-MM-DD.md` 工作日志按规则满 30 天才冷凝，别提前动**——
  压缩掉的是"当时怎么走到这一步"的痕迹，无法复原。

## 坑（按顺序很重要）

1. **切分/治理脚本必须落在 `.py` 文件里再跑**，绝不用 `python -E -c "..."` 内联。
   Git Bash 对**双引号内的反引号**做命令替换，会把 `` `体系/*.md` `` 当命令执行后**替换成空串**写进文件。
   治理当天就是指着这条踩的（日志被静默吃掉 5 处）。
2. **不要在一条消息里对同一文件发多个 Edit**——并行执行互相覆盖，工具全报 success。
   多处改动用**一次性幂等补丁脚本**（原子写 + 旧串命中计数断言 + 回读）。
3. **校验器自身会出 bug**：第一次跑就暴露了路径写死（忘了项目/`~/.workbuddy` 两级目录不同）
   和标题字节级匹配太严。**先让它报错、再修，不要放宽容差去迁就错误数字**。
4. 执行力用户明确指挥——文件是否删除要经过用户确认；旧备份即使不影响注入也别擅动。
5. **校验器自身会失效或误报**（三种表现）：
   - 中文标点（「」。、）在 `0x3000-0x303F`，**不是乱码**。只查控制符 `<0x20`、希伯来/阿拉伯区、私用区、
     `0xFFFD/FFFE/FFFF`。误报会让你对着全是红叉的输出失去判断力。
   - 我自己生成长中文 md 时会偶发**无意义英文词混入**（实测出现过两次，如把补语写成英文动词）。
     grep 不出来，只能肉眼扫——写完回头通读一遍比事后修补便宜。
   - 移走文件后，**校验脚本自己引用的路径会失效**（`memory_path` 已改名却在别处还被调用 → `NameError`）。
     改完必须重跑，不能假设。
6. **输出中文别加 `-E`**：`-E` 会忽略 `PYTHONIOENCODING`，中文变 GBK 乱码。
   改成 `PYTHONUTF8=1 python script.py`（装包时才必须 `-E`）。
7. **★ 真删归档前，先冻结校验基准**——零丢失校验依赖「原文有哪些小节」这个事实，
   原文一删就无从对账。做法：删之前把原文 `## ` 标题提取成 json 基准文件，校验器改读它。
   副作用是校验反而**更严**：可寻址范围不再含原文备份，内容必须真的还在索引卡或专题文件里。
8. **★ 删目录前先查有没有活跃脚本往里写**——否则删完跑一次重跑链，目录自己长回来。
   实测：`build_core.py` 每跑一次就 `makedirs(归档/…/_修复前备份)` 并 copy 原件，
   归档删掉后立刻被重建。查法：`grep -rn "makedirs.*<目录名>" --include="*.py"`，
   找到就把落点改到别处再删。
9. **删目录报 `rc=120` / `WinError 5` 时**：多是**目录被某进程持有句柄**，不是路径错。
   不要改用 `rm -rf` 硬删兜底——退化成「**逐文件**删 + 删空目录」往往可行（实测全部成功）。
   送回收站用 `SHFileOperationW` + `FOF_ALLOWUNDO`，全程保持可恢复。
   ★ **`rc != 0` 不等于没删掉**：实测一次 rc=120，实际已删掉 63 个包中的 61 个，只剩 2 个空壳。
   所以**以复核为准**（目录还在不在、里面还剩几个文件），不要只看返回码就重跑或改硬删——
   重跑会对已删项报 `rc=2`（找不到文件），容易被误读成「删除失败」。
10. **删除不可逆前先做「还原演练」**：留底的价值取决于**能不能真还原**，不是有没有那个文件。
   技能包/配置类打包成 zip 后，至少解压到临时目录验一遍（条目数 + 关键文件可读），再删源。

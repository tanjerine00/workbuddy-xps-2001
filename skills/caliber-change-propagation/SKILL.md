# 顶层口径变更的落地工作流

## 一句话结论

**口径变更不是「改个常量重跑」，是一次横跨数据、脚本、文档、展示层的迁移。**
顺序反了（先动手后量化）会做出不可逆的错误决定；顺序对了（先量化 → 再裁剪 → 再改脚本 → 只改唯一数据源 → 文档分层处理）就是一次干净的迁移。

**本工作流的核心不是「怎么改」，是「改之前必须先证明：这个改动会不会把结论改掉」。**

---

## 〇、触发场景

用户的说法通常是这几种：

- 「交易数据一律按 2024 年 1 月 1 日起算，之前通通忽略；财务数据从 2020 年起。整个体系以这为铁律全部调整过来。」
- 「口径统一一下，全项目都用东财，别混。」
- 「汇率改成逐日的，别再用固定值。」
- 「把 3 年窗口的结论全部重算。」

**旁证信号**：项目里同一指标在不同文件里读数打架（例：`1462 天` / `1145 天` 两组读数各出现在不同报告里）。
出现这个信号 = 口径已经分叉了，不是「文档没同步」。

---

## 一、七条核心原则

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **先量化冲击，再执行** | 裁剪是不可逆动作（配合了归档之后才是可逆）。量化能提前暴露「裁完样本就废了」这类致命后果 |
| 2 | **原件归档，不删除** | 归档件是「原结论有据」的凭据；删除等于销毁证据链 |
| 3 | **窗口收窄要留技术例外，但例外必须锁死用途** | 指标回看（最长 250 交易日）与判断窗口是两个不同的东西，混为一谈会废掉整个窗口的数据 |
| 4 | **只改唯一数据源；渲染壳字节数必须不变** | 渲染壳一变，说明数据又渗回展示层了，数据驱动就白做了 |
| 5 | **活文档改写，历史报告只加横幅** | 「禁止静默改写历史」——历史报告是「当时是怎么说的」的证据，改了就失去对照价值 |
| 6 | **缺口/跑不通的抽出来让用户拍板，不要硬啃** | 用户明说「不要浪费时间」；硬啃消耗算力还会产出低置信度结论 |
| 7 | **重跑恒等式自检，冲突如实登记不平滑** | 新窗口意味着旧的自检比例（如 `120/126`）全部失效，必须重算；不达标的天数**如实登记** |

## 二、执行顺序（七步，别调换）

### 步 0 · 先写口径定义文件，把「边界规则」定死

新建一份规范文件（如 `体系/时间口径铁律.md`），必须包含：

1. **起点表**：每类数据各自的起点。
2. **边界规则（只有一条判据）**：**看数据按什么频率生成**。
   - 按**交易日**生成 → 交易类 → 短窗口
   - 按**报告期**生成 → 财务类 → 长窗口
   - ★ 必须逐项点名易错项。实测踩过的：**限售解禁**虽是"事件"，但由公告与股本结构驱动、来自定期披露 → 归**财务类**；**大宗交易**逐日成交 → 归**交易类**。
3. **技术例外条款**（见 §三）。
4. **执行方式**：脚本路径、归档路径、命名规则。
5. **覆盖现状表**：逐项写「铁律要求 vs 实际可得 vs 状态」，把源限制项标出来。

### 步 1 · ★ 量化起点冲击（**这步不能跳**）

写一个 triage 脚本，对**至少四档起点**跑同一套回测，输出「样本日 / 指标缺值 / 独立事件 / 超额均值 / 超额中位 / MDE / 置换 p」。

实测样例（把交易窗口从 2021-09 收到 2024-01）：

| 档位 | 样本日 | 指标缺值 | 独立事件 | 超额中位 | MDE | 置换 p |
|---|---|---|---|---|---|---|
| A 无限预热（上界） | 593 | 0 | 15 | −1.74% | 12.49% | 0.018 |
| B 1 年预热 | 593 | **7** | 15 | −1.74% | 12.49% | 0.018 |
| C 严格新起点（无预热） | 593 | **249** | 13 | −1.74% | 13.62% | 0.011 |
| REF 原口径（将废止） | 1145 | 0 | 26 | −1.38% | 7.61% | 0.076 |

**这张表一次给出三个决定**：

1. **要不要开技术例外**（B vs C：缺值 7 天 vs 249 天）。
2. **新口径下结论是否改变**（一行行对比超额中位）。
3. **有没有意外的收益**（见下）。

**★ 必看的一列是「超额中位」，不是「超额均值」。**
实测：四档的**超额中位全为负**（−1.38% ~ −1.74%）→ 证明「结论不成立」这件事**对起点选择不敏感**，不是样本挑出来的。
**这条稳健性证据比任何一个单次回测都值钱**——它把「换口径是不是把结论换掉了」这个问题一次答死。
均值会因个别极端事件漂移，中位不会；四档中位同号 = 结构性事实。

**★ 顺手检查：新窗口有没有暴露被长窗口掩盖的事实。**
实测两个例子：
- 旧的半年窗口说「融资余额较 5/25 峰值 −26.48%」；放到 2.7 年窗口里，峰值其实是**一年前的 2025-09-24**，真实回撤 **−31.29%**。两个都对，但单说一个会误导。
- 旧的半年窗口说「融券余量在增加 +71.5%」；放到 2.7 年窗口里是 **385.9 万股 → 47.5 万股（−87.7%）**。
  ⇒ 「在增加」只是从多年低位的一次反弹 → **信号状态必须从 🔴 改 🟡**。
  **收窄窗口反而暴露了长窗口的掩盖** —— 这是必须回报给用户的东西，不是副产品。

### 步 2 · 幂等裁剪 + 归档

```python
# apply_time_rule.py（幂等：可重跑，第二次是 no-op）
# 1) 把原件整体移入 归档/YYYY-MM-DD_<描述>/（shutil.move，不是 os.remove）
# 2) 主口径文件写回数据目录，文件名里的日期区间同步改成真实区间
# 3) 已在窗口内的文件不动（幂等）
# 4) 事件类数据就地裁剪
```

要点：
- **归档目录名带日期与原因**（`归档/2026-09-20_全历史_按铁律停用/`），便于日后回溯。
- **文件名必须改**：`_2020-09-01_2026-09-18.csv` → `_2024-01-01_2026-09-18.csv`。文件名不改 = 下一个人一定误引。
- **预热窗单独存一个文件**（`*_预热_2023.csv`），命名上就与主口径区分开。

### 步 3 · 补齐窗口内可补的数据（用户往往要求「类型全面」）

不要只做减法。旧数据里「只取了半年」的项，在新窗口下**应当补满**。

实测：融资融券 127 行 → **653 行**（源本身有全历史，之前只是没取）；龙虎榜 1 条 → **3 条**。
**补齐动作本身会修正旧记录**——实测补齐后发现「某三个指数其实早就取到了」，此前记为「未取」有误。

> 教训：**说「没取到」之前，先回读原文件确认。** 把「没查」误报成「查不到」会污染缺口登记表。

### 步 4 · 批量改脚本口径

写一个 `patch_scripts_rule.py`：

- 改**文件名引用**（旧路径 → 新路径）+ **START 常量**。
- **已废止的旧脚本加警示头**（不删，注明「口径已废止，见 XXX」）。
- 逐个文件做**语法自检**（`ast.parse` / `node --check`），统计「N 个脚本，0 语法错误」。

### 步 5 · 重跑 + 逐项核对恒等式

- 重跑回测与统计脚本，产出 JSON（便于后续页面/文档引用同一份数）。
- **重算全部自检比例**：旧口径的 `1462/1462 零越界` / `120/126 恒等式成立` **一律作废**，必须重算为新窗口的值（实测 `653/653` / `625/652`）。
- **不达标的天数如实登记，不平滑、不插值**（这是项目铁律）。

### 步 6 · 只改唯一数据源 + 渲染字段名对齐

- 改数据源（`系统数据.js` / `window.X`），**HTML 渲染壳字节数必须不变**。
- ★ **必踩的坑**：渲染器期望的字段名（`e1/n1/e3/win5/bl5`）与新数据的字段名（`exc/exc_med/n/win/bl`）不一致 → **页面表格渲染成空白，但不报错**。
  **改渲染壳去适配新数据，不要改数据去迁就旧渲染器**（后者会把口径退回去）。
- 若字符串精确匹配失败（JS 里的转义差异），改用**边界定位**：`t.find(起标记)` / `t.find(止标记)` 再切片替换，别硬拼长字符串。

### 步 7 · 断言回归 + 文档分层回写

- 断言脚本必须包含**「数据外置检验」**：断言 HTML 源码里**不含**任何结论数字。
  实测这条抓到了渲染壳里一个硬编码的 `593 天`。
- 文档分两层处理（见 §四）。

## 三、技术例外条款怎么写才不算「开口子」

指标需要长回看（如 250 个交易日），若数据严格从新起点开始，**整个窗口第一年的长周期指标全是空的**。

**必须做的三件事**：

1. **量化代价**：算「指标缺值天数 / 样本日」（实测 249/593 = 42%）。
2. **量化收益**：算「加预热后缺值降到几天 / 独立事件恢复多少个」（实测 7 天、13→15），并明确**不新增任何抓取成本**。
3. **锁死用途**：写明「预热窗文件**只允许被指标的取数函数读取**，不得进入任何判断或结论」，并且**文件名上就区分开**。

在规范文件里把它写成**技术必需**，而不是铁律的例外：

> 预热窗是技术必需，不是铁律的口子。真要严格到 2024-01-01，代价是废掉 42% 的样本日；
> 加 1 年预热的代价只是多留 242 行、不新增抓取。

### 三·补 ★ 另一类例外：**用户点名要「超出铁律边界」的样本**

与上面的「技术必需」不同，这类是**用户主动要一个违反铁律的样本**（实测场景：铁律定「交易类数据自 2024-01-01 起」，
用户却说「**2020Q3 起，N=24，完整跑起来**」）。**不能直接照做，也不能一口回绝** ——
它必须同时满足**三条件**，缺一即退化成「**静默改口径**」（最坏的一种：数字看着对、口径已经错）：

| # | 条件 | 落地形式（实测） |
|---|---|---|
| 1 | **用户明示** | 留有原话与日期，**不靠推断**。记进台账时**把原话引出来** |
| 2 | **物理隔离** | 数据落**独立目录**（`数据/_长历史/`）**不覆盖**权威文件；装载走**独立模块**（导入后覆盖全局、**不修改**在役脚本）；报告头部**强制**印「⚠ 口径偏离声明」 |
| 3 | **与在役段存在可机器对撞的重叠区** | 例外段与在役段必然有交集（如 2024-01-01 之后）⇒ **必须**在该交集上做**逐值对撞**，不一致即说明污染了在役口径 |

第 3 条是最容易被跳过、也最关键的一条：**没有重叠区对撞，「没污染」就只是一句自我声明**。
实测做法：例外版报告的 2024／2025／2026 三档起点，**必须**与既有在役报告的同一批数字
**逐值一致**（实测 **66/66（生成器自校）＋ 48/48（独立复算）**）。

同时要在台账里**写清它不构成对既有 ⛔ 结论的翻案** —— 实测同项目里另有一条
⛔「把样本从 5 年拉到 22 年：与铁律『覆盖时间不宜过长』冲突，已废止」，
两者**方向相同但性质不同**（那条是「无明确指令下自行拉长」，本条是「用户点名的样本」），
**必须并列写明**，否则日后一定会被误读成「既然能拉到 2020，那 22 年也能拉」。

## 四、文档分层处理：活文档改写，历史报告只加横幅

这是本工作流最容易被做错的一步。**不要全局替换。**

| 层 | 判据 | 处理方式 |
|---|---|---|
| **规范文件** | 定义口径的文件 | **新建**（口径变更的锚点） |
| **活文档**（台账 / 总纲 / 待办 / 素材账本 / 框架） | 描述「现在是什么」 | **改写**：重算读数、标注废止项、加版本记录行、指明新口径文件 |
| **历史报告** | 某一次分析的交付物 | **数字一字不改**，只在文首加「口径已废止/已变更」横幅 + 指向新报告 |
| **追加型日志** | 重跑日志 | 不动（追加即可） |
| **自动生成文件** | 每次重跑覆盖的文件 | 不动（重跑即更新） |

**横幅模板**（历史报告）：

```markdown
> ⚠ **口径已废止（YYYY-MM-DD）**：本文基于「<旧样本>」的旧口径。
> 用户已于 YYYY-MM-DD 定调 **<新口径名>**，该口径不再适用。
> 本文**保持原样、不改写**（作为「当时是怎么说的」的证据）。
> **现行读数以 `<新报告路径>` 为准**（<新样本>）。
> <哪些定性结论仍然成立 / 哪些读数必须替换>
```

**为什么要分两层**：用户后来问「你当时是怎么说的、为什么改」，只有保留原样的历史报告能回答。
把历史报告一起改掉 = 系统失去了自己的审计轨迹。

## 五、幂等补丁脚本的写法要点

同一文件多处改动**绝不能**并行发多个 Edit（实测：并行互相覆盖，且工具**全部报 success**，只落盘一部分）。

正确做法是**一次性幂等补丁脚本**：

```python
def apply(path, reps):           # reps = [(old, new, expected_count), ...]
    t = open(path, encoding="utf-8").read()
    orig = t
    ok = True
    for old, new, cnt in reps:
        c = t.count(old)
        if c != cnt:             # 命中数不对 → 报错并放弃该文件
            print(f"  ✗ 命中 {c} 次（期望 {cnt}）：{old[:60]}…")
            ok = False
            continue
        t = t.replace(old, new)
    if not ok:
        print(f"  ⇒ 放弃写入 {path}（有未命中组）")   # 关键：整体放弃，不写半成品
        return False
    with open(path, "w", encoding="utf-8", newline="\n") as f:
        f.write(t)
    back = open(path, encoding="utf-8").read()        # 回读校验
    assert back == t
```

三个关键点：

1. **逐组核对「旧串命中次数」**，不符即**整体放弃该文件**——不写半成品。
2. **落盘后回读比对**（`assert back == t`）。
3. **换行符先实测再定，逐文件保留原风格**：先 `b.count(b"\r\n")` 再决定写回方式。
   ⚠ **无脑 `newline="\n"` 是错的**（2026-09-22 实测：同一个项目里 `中芯国际分析系统.html` 是 CRLF，
   其余多为 LF）→ 把 CRLF 文件整体改成 LF 会凭空产生大 diff。

**踩过的坑**：
- 引号/转义差异会让精确匹配失败 → 改用**边界定位**（`find` 起止标记 + 切片）。
- **追加式替换的计数判据不一样**：不是「旧串必须为 0」，而是 `count(旧) == count(新) × 内含次数`。
- 「括号前后必须相等」是错的判据（新增内容本来就会让计数涨），只要求**各自配平**。
- 本机 stdout 默认 GBK，且 `python -E` 会**忽略** `PYTHONIOENCODING` → 脚本里第一行就 `sys.stdout.reconfigure(encoding="utf-8")`。
- **★ 幂等判据必须「先查 new」**（2026-09-22 实测）：当编辑是「在某行/某表末尾**追加**一行」时，
  **旧串恰好是新串的前缀**（新串 = 旧串 + 追加行）→ 重跑时 `count(old)==1` 仍成立，于是**又插入一行**。
  实测代价：一次重跑让「裁定表第 4 行」「漂移表 EV/EBITDA 行」各**重复一次**，须写去重脚本恢复。
  修法：`if new in t: continue`（先判 new），再查 old。**凡「追加式」编辑一律用这个判据。**
- **★ 旧串别带尾换行、新串别漏尾换行**（2026-09-22 实测）：若 `old` 以 `\n` 结尾而 `new` 不以 `\n` 结尾，
  替换会**静默吞掉一个换行**，把两行粘成一行（实测：`findings: [` 与下一行 `{` 被粘住 → 变成 `findings: [    {`），
  更糟的是它会让**同批次后续编辑的锚点全部失配**（报「旧串未命中」，看起来像自己写错了）。
  规则：`old` 与 `new` 的**首尾换行必须逐一对应一致**。
- **★ 改 `old` 时必须同步核对 `new`（两者是原子对）**（2026-09-22 第三次实测）：一次修复里，
  `old` 串写错（多写了一个行首标签）→ 只把 `old` 改对、**忘了 `new` 里同一处也要改** →
  「先查 new」判据立刻失灵（`new` 与实际落盘内容不一致）→ 重跑被判为「未应用」而**再插一次**，
  且新插入的串带着那份错误的 old 副本。
  实测代价：总结文件里同一行**重复 2 次** + 另一行首列被写成错的标签，须再写第二个清理脚本才恢复。
  规则：**修一个编辑项时，`old` / `new` 一起看——改一个必须核对另一个**；
  并在补丁跑完后**再跑一次**验证「全 skip、rc=0」，这是唯一能自动抓到该类的验收。
- **★ 行级替换（insert-after）的判据不能只看「前缀行」**（2026-09-22 第四次实测）：
  用「行首前缀」定位整行时，若编辑是**在该行之后插入新行**，则**前缀行本身内容不变**
  ⇒ 「查 old」「查前缀行是否等于 new」两种判据**全部恒成立** ⇒ 重跑**又插一次**
  （实测：体系总纲的南向行被写进 2 遍）。这是「先查 new」之外的**第三种失效形态**。
  正确判据：**`new_body` 的首行是否已存在于文件中**（与用哪个前缀定位无关）：

  ```python
  first = new_body.split("\n")[0].rstrip()
  if any(ln.rstrip() == first for ln in lines):
      return True          # 已应用，直接跳过
  ```

  ⚠ 配套陷阱：**不要**把 `new_body` 写成「保留不变的原行 + 新行」——
  那样 `first` 就等于原行，**第一次运行就会被误判为已应用**、什么都插不进去。
  追加式编辑应把**新行单独**放进 `new_body`，用 `mode="insert_after"` 的语义，而非拼串。

### ★ 配平自检不算数：JS 类文件改完必须跑 `node --check`（新增，血泪）

**「括号配平」抓不到「少一个逗号」——而少一个逗号会让整个对象字面量解析失败、文件全废。**

**实证（2026-09-20）**：往 `系统数据.js` 的 materials 数组里插入一条新素材时，
新对象开头的 `{` 与上一条的 `}` 之间漏了逗号。补丁脚本的**括号配平自检正常通过**（配平确实没坏），
于是落盘"成功"。**结果整个数据文件解析失败**，页面 44 项断言里**只过了 5 项**（数据全空）。
诊断成本远高于当初多跑一行命令。

**规则**：凡是 `.js`/`.json`/`.ts` 这类**结构化**文件，补丁后**必须**加一步语法硬检：

```bash
node --check 系统数据.js && echo "语法通过"
```

再跑页面/接口验收。**顺序不能颠倒**：
```
补丁落盘 → node --check（语法）→ 断言回归（语义）→ 才算改完
```
**判断标准要记牢**：验收时出现「**大面积、跨模块同时失败**」（尤其原本已通过的项突然全红），
**先怀疑文件解析失败，不要逐个去查业务逻辑**——那是浪费时间的方向。

Git Bash 下 `python -E -c "…"` 里的 `\s` `\d` 会被转成 `/s` `/d`，正则直接语法错误：

```
bash: syntax error near unexpected token `('
    ids=re.findall(r'id:/s*/"([A-Z]-0/d)/"', t)
```

**对策：一律把探测/补丁脚本写成文件再执行，不用 `-c` 内联。**
同理，搜中文一律用内置 Grep 工具（Git Bash 的 `grep` 会转码，给出假 0 或假命中）。

## 七、反例：这一步最容易自欺的地方

| 自欺方式 | 后果 | 正确做法 |
|---|---|---|
| 只报「均值超额」，不报中位 | 均值被 1~3 个极端事件拉起，看起来有效 | **均值与中位一起报**；两者裂开就是「靠极端值撑起」 |
| 用「改了数据页面变了」当验收 | 渲染壳可能自己藏着硬编码数字 | 断言「**HTML 源码不含结论数字**」 |
| 把历史报告一起改掉 | 失去审计轨迹，日后无法回答「当时怎么说的」 | **只加横幅，不改数字** |
| 只验证「页面能打开」 | 字段名不匹配时表格渲染成空白但不报错 | 断言**关键数字已渲染**（如 `+3.81%` / `MDE 12.48%`） |
| 把「没查」当成「查不到」 | 污染缺口登记表，让用户为不存在的问题做决策 | **下结论前回读原文件** |
| 直接开工裁剪 | 可能废掉 40% 样本而不自知 | **先跑四档 triage** |

## 十、★ 固定假设类口径的专项检测（汇率 / 税率 / 折算率 / 单位换算）

**不是所有口径变更都是「换时间窗口」。** 更隐蔽的一类是**「用一个固定假设值代替逐日实测值」**——
例：A/H 溢价用固定汇率 0.9180、财务折算用固定 7.8、估值用固定所得税率。

**这类口径最危险的地方：它不会报错。** 序列照样算出来、图照样画、结论照样写，
只是**读数在时间上系统性失真**，而且**越到近期越失真**。

### 10.1 ★ 时间漂移检测（核心手法，别跳）

**固定值的问题从来不是「一直偏」，而是「越偏越远」。** 所以不要只比一个点，要**按年比**：

```
对每个自然年，算：实测值年均  →  相对假设值的偏差 %
看偏差是否单调扩大。
```

本轮实测（港元人民币中间价 vs 固定 0.9180）：

| 年份 | 实测年均 | 相对假设值偏差 |
|---|---|---|
| 2024 | 0.9128 | +0.57% |
| 2025 | 0.9162 | +0.20% |
| 2026 | 0.8759 | **+4.81%** |

→ **判定**：假设值在 2024–2025 是**可接受的近似**，2026 **失效**。
→ 这个结论和「假设值总体偏了多少」完全不同，直接决定「要不要动手」和「怎么描述影响范围」。

**如果只看全期均值，会得出「平均偏差才 1.9%、不用改」的错误结论——正是这个错误上一轮被写进了文档。**

### 10.2 偏差的传导方向要算对

固定值代入的是**分子还是分母**，决定偏差放大还是缩小。以 A/H 溢价为例：

```
溢价 = A ÷ (H × FX) − 1      FX 偏大 → 分母偏大 → 溢价偏小（低估）
反算：真实溢价 = (1 + 溢价_假设) × (假设值 ÷ 实测值) − 1
```

**必须显式写清传导方向**，否则会误判「偏了 4.8%」到底是高估还是低估。

### 10.3 ★ 占位值污染检测（本轮意外收获）

**任何「序列在非交易日仍有值」都要查是不是占位填充。**

本轮实例：第三方文件在中芯 A 股**停牌 6 个交易日**（2025-09-01~09-08）期间，
填入了 **114.76 的占位 A 股价**（正是停牌占位价），于是凭空算出 6 个「停牌期 A/H 溢价」——
**这些读数根本不存在**。

检测法：
```python
# 停牌识别（OHLC 全等 + 量为 0/空 —— 与「一字板」区分靠成交量）
if o == h == l == c and (not vol or float(vol) == 0):
    continue
```
**处置**：清空该日字段 + 加 `susp_flag` 标记列 + 原值写 JSON 留痕归档（不静默删）。

### 10.4 官方接口限历史 → 用「近一年零偏差」推定全期

很多官方源**只提供一年历史**（CFETS 中间价接口 `flagMessage` 明写「只提供一年历史数据查询及下载」，
超出范围直接返回空 `records`，**不报错**）。

**应对**：
1. 抓满可得的近一年，与主源**逐日对撞**；
2. 若**零偏差**（本轮 241/241），则「同接口、同字段、无断层」→ **可推定**更早段落同样可靠；
3. **但必须在文档里如实标注**：近一年=双源，更早段=**单源（依赖推定）**。
   **不得因为推定成立就省略这个标注。**

### 10.5 内部一致性检验（零成本、抓错能力极强）

找两条应满足固定关系的序列，验证关系成立。本轮：
```
USDCNYC ÷ HKDCNYC 必须落港美联系汇率带 7.75–7.85
实测 660 天全落 7.7511~7.8502，仅 10 天微越界（7.8500~7.8502）
且全部集中在 2025-06~08 —— 那正是港元触及「弱方兑换保证 7.85」的时段
```
→ **越界不是错误，是市场事实。** 这条检验的妙处：**数据若是编的，不会精确在 7.85 附近聚簇。**
→ 通用化：`A ÷ B` 应落某个已知区间时，就去验它；**边界附近的聚簇是真实性的强证据**。

### 10.6 口径选择必须显式写出，不能默认

同一个量常有多个口径，**差异可能大到影响结论**：

| | 中间价（本轮采用） | 即期价 |
|---|---|---|
| 性质 | 官方基准 | 市场成交价 |
| 覆盖 | 660 天零缺口 | 仅 410 天（覆盖不全） |
| 可验证 | ✅ 与官方零偏差 | 无法取长历史对撞 |
| 差异 | — | **约 1.9pp** |

**规则**：
- 首选「**可交叉验证 + 覆盖完整**」的那个；
- 但**必须写进文档**：`⚠ 中间价 ≠ 可交易即期价`；
- 另一个口径的差异幅度与取得障碍也要列出来，作为**可选项**交用户拍板，不要悄悄替他决定。
- 用户拍板后**必须收口**（结论改「已关闭」+ 记明理由），不能长期挂在「可选项」状态 —— 见 §10.9。

### 10.7 顺带找「口径混用」的痕迹

改动前先搜一遍项目里该指标的**所有**出现位置。本轮搜出一个典型：
文档里写「实测 **117.59%**（2026-09-18）」—— **而逐日汇率算出的正是 117.59%**。
说明上一轮核证时**单日用了真汇率、建成序列时却换成固定值**：
**同一份报告里两种口径并存**。这类混用只有逐字搜才能发现。

### 10.8 交付检查（在 §九 之外追加）

- [ ] 固定假设值已按年比对过实测值，**偏差趋势已量化**（不是只算总均值）
- [ ] 偏差的传导方向（高估/低估）已写清
- [ ] 非交易日占位值已排查，命中的已清空 + 留痕 + 加标记列
- [ ] 官方源限历史时，双源段与单源推定段**已在文档中分别标注**
- [ ] 口径选择（中间价/即期等）已显式写出，未采用的那个作为可选项交用户
- [ ] 已搜过全项目该指标的出现位置，排查「单日用真值、序列用假设值」式混用
- [ ] 用户拍板后，结论已写成「**已关闭**」并记明放弃理由（不是留在「可选项」状态）

### 10.9 ★ 用户拍板后要「关闭」，不要留在「可选项」状态

按 §10.6 把另一个口径作为可选项交用户拍板是对的，但**拍板之后必须收口**。收口要写三样东西：

1. **结论从「待决/可选」改成「已关闭」**，并把**放弃的理由逐条写进去** ——
   口径性质、覆盖天数、差异幅度、取得障碍。理由是防止它被重新翻出来重议的**唯一屏障**。
2. **留下「被否方案」的记录**：放弃可选项 ≠ 删资料。已抓到的备用序列留在原文件里、
   注明「**不参与任何结论**」，情况变了可随时重启。**删除是单向的，标注是双向的。**
3. **立一条系统规则，而不是口头约定**：本轮之前，同一个项目已**三次**经历口径反复 ——
   固定汇率 0.9180 → 逐日中间价、H 股扩 22 年方案废止、建仓雷达阈值校准停止。
   故把「**拍板项不重开、被否方案连理由记台账**」写成规则条目 + 断言（如
   `r.ruleText.indexOf("不纳入即期") >= 0`），让「已决定」这件事**可被机器验证**。

**为什么这条值得单独写**：没有收口的口径，几轮之后会被重新提出，白白消耗一轮算力与注意力；
而**「上次为什么否掉」一旦没落盘，就再也找不回**。**决策的理由比决策本身更容易丢。**
